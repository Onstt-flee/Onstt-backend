# Pi 5용 Q4/Q5 GGUF 변환 및 dev72 회귀 결과

## 결론

GPU 서버에서 `Qwen3-4B-Instruct-2507`과 v0.2-D PEFT LoRA를 각각 `Q4_K_M GGUF`와 `F16 GGUF LoRA`로 변환했다. 베이스와 LoRA의 동시 로딩, OpenAI 호환 모델 alias, 일본어 판단 1건은 정상 동작했다.

Q4의 72문항 개발셋 회귀는 구조 계약 71/72로 필수 기준에 한 건 미달했다. 상위 정밀도 후보 Q5_K_M를 별도 생성해 동일 조건으로 실행한 결과 구조 계약과 GPU BF16 판단 일치가 모두 72/72였고 양자화 회귀 게이트를 통과했다. Q5는 Pi 하드웨어 성능시험 후보일 뿐 아직 오프라인 대체 경로 승인 모델은 아니다.

## 로딩 스모크

`llama-server`가 Q4 모델과 GGUF LoRA를 함께 로드했고 `/v1/models`에서 alias `judgment-v02d`를 반환했다. `JG-001`은 `acceptable`, 원문 보존, 빈 edit/error type으로 v0.2 계약을 통과했다. x86 CPU 스모크 지연시간은 12,544.354ms였으며 Pi 성능 근거로 사용하지 않는다.

LoRA 텐서가 CPU_REPACK 버퍼를 직접 사용하지 못해 일반 CPU 버퍼로 폴백한다는 경고가 있었지만 로딩과 추론은 성공했다. Pi에서도 실제 ARM 빌드 로그와 메모리·발열을 별도로 확인해야 한다.

## 유일한 실패와 처리

`JG-014`의 원문 `この町は静かで、住みやすいです。`에 모델이 `needs_correction`과 `adjective_conjugation`을 반환하면서 `corrected_text`는 원문 그대로 유지했다. 이는 “교정 필요라면 실제 최소 교정이 존재해야 한다”는 계약에 모순된다.

백엔드가 판단을 `acceptable`로 덮어쓰지 않는다. 현재 1회 재시도 정책은 비교정 판단이 원문을 훼손한 경우에만 적용되므로 이 오류도 자동 재시도하지 않고 503으로 차단하는 것이 맞다. 이 한 건을 숨기기 위해 출력 파서나 게이트 기준을 완화하지 않는다.

판단·교정문 모순까지 1회 재시도하는 확장안을 별도 실모델 진단으로 시험했다. 두 번째 호출도 동일하게 `needs_correction`과 원문 그대로인 `corrected_text`를 반환해 `attempt_count=2`, `retry_used=true` 상태로 최종 계약 실패했다. 계약 성공률을 개선하지 못하고 지연시간만 늘리므로 코드 변경은 전부 되돌렸으며, 기존 비교정 원문 보존 재시도 정책만 유지한다.

## 다음 단계

1. Pi로 Q5 모델·LoRA·Q5 후보 manifest를 전송하고 해시를 재검증한다.
2. Q5 manifest는 기본 preflight에서 거부되며 후보 시험 때만 `--allow-candidate-q5`를 명시한다.
3. Pi ARM에서 모델+LoRA 스모크와 50건 p95·RSS·발열 시험을 수행한다.
4. 성능 기준까지 통과하면 Q5를 Pi 오프라인 후보로 승격할지 결정한다. 그전까지 Q4 배포 기본값과 GPU 기본 경로는 변경하지 않는다.

전송·시험을 위한 `pi5-q5-candidate.env.example`을 별도로 두었다. outbox와 GPU 수신기는 Q4/Q5를 모두 검증하되, 환경에 명시된 양자화 형식을 모델·어댑터 해시와 함께 provenance에 보존한다. 50건 요약은 원시 JSONL의 해시까지 기록하므로 문장 내용을 Git에 넣지 않고도 어느 실행을 판정했는지 확인할 수 있다.
