# feedback-v0.1 LoRA의 holdout v0.2 평가 결과

기준일: 2026-10-15

## 결론

`feedback-verifier-v0.1`은 구조가 다양한 holdout v0.2에서 **미채택**이다.
reasoning parser로 출력 래퍼 문제는 거의 해소됐지만 strict 계약과 검수 품질 기준을
모두 충족하지 못했다. 기능 플래그는 비활성으로 유지하고 200건 shadow, 관리자
반복 오류 경고, 자동 학습 후보 생성에는 사용하지 않는다.

## 실행 고정값

- 데이터: 자동 생성·검증 120건, 사람·전문가 검수 아님
- holdout SHA-256: `44a8dec5f4cf49a730c85c9d8be8c04e8be7013d43ba2ecc742c129059282358`
- 사전 봉인 커밋: `5ff3393`
- 모델: Qwen3-8B BF16 + feedback-v0.1 LoRA
- 배포 조합 SHA-256: `efbbc9d2cf2bed81e6ce24da6070c25d7bc0755c213875224cfa204d58a22630`
- vLLM 0.28.0, `--reasoning-parser qwen3`
- `VLLM_USE_FLASHINFER_SAMPLER=0`
- temperature 0, max tokens 512, 순차 실행 1
- 공식 모델 호출: 120건, 재실행 없음

첫 서버 기동은 FlashInfer 0.6.16의 sampling JIT와 설치된 CUB 헤더가 충돌해 모델
요청 전에 중단됐다. 저장된 서비스 설정과 같이 FlashInfer 샘플러만 비활성화한 뒤
정상 기동했다. 홀드아웃이 아닌 학습 입력 1건으로 content 분리를 확인한 후 공식
실행을 시작했다.

계약 실패는 2건이다. 한 건은 비교정 권장인데 원문을 보존하지 않았고, 한 건은
`issue_codes`를 중복 생성했다. verdict 혼동은 `agree→disagree` 16건,
`disagree→agree` 16건, 계약 실패 2건이다. 올바른 판단 31건 중 15건만 동의해
과도하게 문제를 찾는 성향이 가장 큰 안전 문제다.

유형별 verdict는 false positive, reason mismatch, wrong error type, unnecessary
abstention을 모두 탐지했지만, 실제 동의 48.39%, false negative 50%,
should abstain 0%였다. 출력 계약만 고쳐서는 운영 검수기가 될 수 없으며 다양한
정상·오류·보류 사례를 분리해서 다시 학습해야 한다.

## v0.1 진단과의 비교

첫 holdout의 빈 think 래퍼 제거 진단은 120/120 만점이었지만 그 시험지는 학습과
같은 12개 구조 템플릿 계열이었다. v0.2는 피드백 학습 입력 및 v0.1 시험 입력과
완전 동일 입력이 0건이고 문장 구조가 더 다양하다. 이번 급락은 v0.1 만점이 일반화
성능이 아니라 템플릿 암기였다는 강한 증거다.

다만 v0.2 원문도 내부 judgment holdout v0.5에서 파생됐고 `source_stratum`은 실제
GPU/Pi 출력이 아닌 모의 표식이다. 따라서 외부 독립 품질이나 실제 양자화 간 격차를
증명하는 결과로 사용하지 않는다.

## 다음 단계

1. 기존 피드백모델은 연구 기록으로만 보존하고 운영 worker를 활성화하지 않는다.
2. 54개 핵심 실패를 `동의 과검출`, `오류 누락`, `보류 실패`, `권장 교정 실패`로
   분류해 feedback-v0.2 학습 설계를 만든다.
3. 새 학습 전에 외부 독립 원문과 실제 GPU/Pi 판단 출력을 포함한 holdout v0.3을
   추론 0회로 봉인한다.
4. 자동 생성 데이터만으로 충분한 보류·문맥 판단을 만들 수 없다면 이 단계에서
   사람 검수를 요구하지 않고 피드백 검수모델 개발을 보류한다.
