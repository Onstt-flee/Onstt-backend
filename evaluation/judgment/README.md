# 일본어 판단모델 최소 평가셋 v0.1

상태: **비중복 실제 STT 100건 계약 재시도 shadow까지 완료, 제한적 staging/shadow 기준 통과**. 최종 계약은 99/100이고 재시도 1건은 회복되지 않았다. 운영 기본값·학습자 노출은 미승인이며 일본어 전문가 검수와 라벨 있는 실제 발화 품질 검증은 아직 완료하지 않았다. 새 `holdout_v0.4`는 모델 추론 0회다.
이 폴더는 운영 `analyzer` 및 DB와 분리된 오프라인 평가 도구와 결과 요약을 담는다.
전체 11개 모델의 비교, 평가 기준과 최종 2개 후보 선정 근거는 [최종 모델 선정 문서](FINAL_MODEL_SELECTION.md)에 정리했다.

## 2. 판단 범위와 경계

이번 범위는 일상 회화의 일본어 텍스트 문법이다. 표준적인 표현과 일반적인 회화체를 허용한다.
문장 길이, 존댓말 여부, 어휘 난이도, 한자 표기 취향만으로 교정하지 않는다.
대명사의 대상이나 생략된 주어가 불명확하다는 이유만으로 문법적으로 성립하는 문장을 보류하지 않는다.

- `acceptable`: 주어진 텍스트의 문법 구조를 고칠 필요 없음. 원문 그대로, 수정 구간 없음. 표기·문체·질문 적합성·발음까지 통과했다는 뜻이 아니다.
- `needs_correction`: 오류와 의미를 보존하는 교정 근거가 명확함. 필요한 부분만 수정.
- `insufficient_evidence`: 발화 중단 등으로 전체 판단에 필요한 증거가 부족하거나 일본어 문법이라는 작업 범위 밖임. 원문 그대로, 수정 구간 없음.

보류 문항의 녹음 중단·잡음 정보도 **합성 시나리오**이며 실제 음성을 확인한 사실이 아니다.
단순히 짧은 응답이라는 이유로 보류하지 않는다. 예를 들어 `京都です。`는 여행지를 묻는 문맥에서 허용한다.
`今日はあめです。`는 문법상 허용하며, 텍스트만으로 あめ의 발음 오류나 STT 오인식을 단정하지 않는다.
음성 자체의 발음 정확도, 원어민 자연스러움 전반, 방언 전반의 판정은 아직 측정하지 않는다.

이 보류는 **정상적인 모델 판단**이다. 네트워크 실패·JSON 파싱 실패는 별도의 시스템 실패이며 이 라벨로 바꾸거나 정답으로 계산하면 안 된다.

필러·문체·STT 표기·동문서답은 문법 판단과 구분한다. 한 줄 기준과 12개 경계 사례는 [경계 기준 문서](BOUNDARY_GUIDELINES.md)를 따른다.
보조 항목은 정답 쪽의 `check:` 태그이며 현재 모델 출력이나 자동 판정 기능이 아니다.

## 3.1 기존 v0.1 출력 계약

입력은 `text`, `context`(없으면 `null`), `learner_level`이다. 모델에 정답·그룹·검수 메타데이터를 전달하지 않는다.
출력은 다음 네 필드만 사용한다.

```json
{
  "decision": "needs_correction",
  "corrected_text": "明日は電車で病院に行きます。",
  "edits": [
    {
      "start": 8,
      "end": 9,
      "source": "を",
      "replacement": "に",
      "error_type": "particle_misuse"
    }
  ],
  "reason_ko": "병원을 목적지로 말하는 문맥이므로 を를 に로 고칩니다."
}
```

이 예의 원문은 `明日は電車で病院を行きます。`이고, 목적지가 병원이라는 문맥이 주어진다.

- 위치는 **원문 그대로의 Unicode 코드 포인트 기준, 0부터 시작하는 `[start, end)`**다. UTF-8 바이트나 JavaScript UTF-16 인덱스가 아니다.
- 삽입은 `start == end`, `source == ""`; 삭제는 `replacement == ""`로 나타낸다.
- 수정 구간은 원문 순서대로 정렬하고 서로 겹치지 않는다. 모두 적용하면 `corrected_text`와 정확히 같아야 한다.
- `error_type`: `particle_misuse`, `verb_conjugation`, `adjective_conjugation`, `copula_conjugation`, `modifier_connection`, `tense_mismatch`.
- `reason_ko`는 짧은 한국어 판단 근거다. 학습자 점수, 장문 해설, 검증하지 않은 확신도 숫자는 요구하지 않는다.
- `accepted_corrections`는 **정답 쪽에만** 있는 허용 교정 후보이며 모델 출력 필드가 아니다. 예를 들어 목적지의 に와 へ를 모두 기록한다.
- 이 후보 목록은 모든 정답 표현을 열거한 것이 아니다. 목록 밖의 교정을 문자열 불일치만으로 오답 확정하지 말고 사람 검수 대상으로 남긴다.

`validate_judgment`는 JSON 객체의 필드·타입·구간·복원 일관성만 검사한다.
문법의 정답, 의미 보존, 최소 교정, 한국어 설명의 타당성을 자동으로 증명하지 않는다.
기존 API의 `is_correct`/`feedback_ko` 계약이나 파서는 변경하지 않았다.

## 4. 검증 명령

기능 플래그 판단 API와 같은 입력 우선순위로 실제 DB를 읽되 결과를 DB에 쓰지 않는 shadow 실행 명령은 다음과 같다. 파일 경로 직접 실행이 아니라 저장소 루트에서 모듈로 실행한다.

```bash
venv/bin/python -m scripts.run_judgment_shadow --limit 50
```

동일한 공식 표본을 결과에 맞추기 위해 반복 실행하지 않는다. 새 실행 전에는 원시·집계 출력 경로와 표본 정책을 별도 버전으로 고정한다.

저장소 루트(`/home/cap-minsung/stt_api`)에서 실행한다. 추가 패키지·모델·GPU·서버가 필요하지 않다.

```bash
venv/bin/python -B -m evaluation.judgment.dataset --rag-dir rag_data
venv/bin/python -B -m unittest discover -s tests -v
```

출력에는 문항 수, 판단·검수 분포, 데이터 SHA-256, 선택한 RAG 중복 검사 결과가 포함된다.
문항 ID·필수 필드·중복 입력·오류 위치·교정문·검수 정보가 잘못되면 종료 코드 1로 실패한다.

```bash
# 익명 사용자 검수 완료 여부 확인: 현재 72문항에서는 성공해야 한다.
venv/bin/python -B -m evaluation.judgment.dataset --require-reviewed

# 정답 없는 입력만 표준 출력으로 내보낸다. 파일 저장이나 모델 호출은 하지 않는다.
venv/bin/python -B -m evaluation.judgment.dataset --inputs-only

# 원본을 수정했을 때 검수용 표의 최신 내용을 확인한다.
venv/bin/python -B -m evaluation.judgment.dataset --review-markdown
```

입력 내보내기의 `id`는 결과를 합치는 키다. 나중의 모델 프롬프트에는 각 행의 `input`만 전달한다.
원본 JSONL 전체를 프롬프트로 보내지 않는다. 검수용 표와 원본이 다르면 회귀 테스트가 실패한다.
도구는 검수 상태를 스스로 올리지 않으며, `--require-reviewed`는 기록된 검수 필드를 확인할 뿐 실제 사람 검수 여부를 인증하지 않는다.

## 5. 독립 모델 실행기

`runner.py`는 운영 `analyzer`와 분리되어 OpenAI 호환 `/v1/chat/completions` 서버를 호출한다.
모델 요청에는 `text`, `context`, `learner_level`만 들어가며 ID와 정답·교정 후보·태그·검수 정보는 전달하지 않는다.
응답 JSON의 필드·타입·edit 복원 일관성은 검사하지만 정답과 비교하거나 점수를 계산하지 않는다.

LLM 서버가 준비된 뒤 먼저 1개 문항으로 연결을 확인한다.

```bash
venv/bin/python -B -m evaluation.judgment.runner \
  --endpoint http://127.0.0.1:1234/v1/chat/completions \
  --model Qwen/Qwen3.5-4B \
  --output evaluation/judgment/runs/qwen35-4b-bf16-smoke.jsonl \
  --id JG-001
```

전체 72문항 실행 시 `--id`를 빼고, 앞부분만 확인할 때는 `--limit 2`처럼 지정한다.
같은 출력 파일이 있으면 기본적으로 실패하며 의도적으로 다시 실행할 때만 `--overwrite`를 사용한다.
인증이 필요한 서버는 토큰 값을 인수에 쓰지 않고 `--api-key-env 환경변수명`으로 전달한다.

결과 JSONL에는 모델에 보낸 정확한 요청, 원시 서버 응답, 추출된 모델 텍스트, 전송 성공 여부, 엄격한 계약 검증 결과와 지연시간이 문항별로 저장된다.
옆의 `.manifest.json`에는 데이터·프롬프트·결과 SHA-256, 모델명, 생성 조건, 실행 환경과 성공 건수가 기록된다.
실행 중 예외가 발생하면 `.partial` 파일을 남기며, 완전한 실행만 최종 JSONL 이름으로 교체된다.
`evaluation/judgment/runs/`는 원시 응답과 대용량 결과가 들어갈 수 있어 Git에서 제외한다.

Markdown 코드 펜스 제거, 누락 필드 보충, 잘못된 교정문 자동 복구는 하지 않는다.
그런 응답은 `contract_valid: false`로 보존하며 독립 채점기에서 JSON 성공률과 시스템 실패에 반영한다.

## 6. 독립 채점기와 비교 보고서

`scorer.py`는 모델을 호출하지 않고 실행 JSONL과 manifest를 평가셋에 대조한다.
먼저 실행 파일·데이터 SHA-256, 문항 ID와 순서, 모델에 노출된 입력 필드, 프롬프트 해시, 생성 조건, 원시 응답과 저장된 계약 판정의 일치 여부를 검사한다.
전송 실패와 JSON/계약 실패는 `system_failure`로 집계하며 `insufficient_evidence` 정답으로 계산하지 않는다.

하나 이상의 전체 실행이 준비되면 다음처럼 보고서를 만든다.

```bash
venv/bin/python -B -m evaluation.judgment.scorer \
  --run evaluation/judgment/runs/qwen35-08b.jsonl \
  --run evaluation/judgment/runs/qwen35-2b.jsonl \
  --output-prefix evaluation/judgment/runs/qwen35-comparison
```

같은 데이터 SHA-256, 동일 문항과 순서, 같은 프롬프트 해시·생성 조건만 기본 비교한다.
의도적인 설정 비교에만 `--allow-mixed-config`를 사용한다.
기존 보고서는 덮어쓰지 않으며 재생성이 확실할 때만 `--overwrite`를 사용한다.
결과는 `.json`과 `.md` 두 파일로 원자적으로 생성된다.

보고 항목은 전송·JSON 계약 성공률, 3분류 혼동행렬과 정확도, 과교정률, 교정 탐지 정밀도·재현율, 올바른 보류율, 명확 문항 처리율, 정규·허용 교정문 일치, edit micro 정밀도·재현율, 복합 오류 누락, 오류 유형·수준·경계 태그별 결과, 지연시간·토큰 사용량이다.
비율에는 분자·분모와 Wilson 95% 신뢰구간을 함께 기록한다.
잠정 목표는 JSON 99% 이상, 과교정 2% 이하, 탐지 정밀도 95% 이상, 재현율 80% 이상, 명확 문항 처리율 85% 이상이다.

`accepted_corrections`는 완전한 정답 목록이 아니므로 목록 밖의 자연스러운 교정을 자동 오답으로 확정하지 않는다.
`reason_ko`의 타당성, 의미 보존과 최소 교정의 언어학적 적합성은 자동 점수가 증명하지 못하며 별도 사람 검토 대상이다.
모델 크기는 manifest에 검증된 수치가 없으므로 자동 순위에 넣지 않고, 같은 조건의 성능을 확인한 뒤 실제 파라미터·메모리 측정과 함께 가장 작은 후보를 선택한다.

### 내용 진단 보조 도구

`content_diagnostics.py`는 모델이 낸 네 필드 JSON에서 판단과 교정문만 비교하고 edit 위치·복원 검증을 의도적으로 무시한다. 엄격 계약 실패가 언어 판단 실패인지 위치 생성 실패인지 분리하는 개발 진단용이며, `scorer.py` 공식 점수를 대체하지 않는다.

## 7. 중복·오염 점검의 범위

2026-09-03 검사: 기존 RAG JSON 4개에서 문자열 6,920개를 읽어 입력·기준 교정문·허용 교정 후보와 비교했다.
초기 중복 1개를 수정한 뒤 **정규화 문자열의 직접 일치는 0건**이었다.
NFKC 적용 후 공백·구두점을 제거하고 4글자 이상인 값만 비교한다.

이 결과는 짧은 표현, 비슷한 문장, 생성 템플릿, 모델 사전학습 데이터와의 중복까지 없다는 뜻이 아니다.
RAG JSON이 바뀌면 다시 검사해야 한다. DB·음성·pickle·모델 가중치는 중복 검사의 입력이 아니다.
첫 모델 비교는 RAG와 기존 `analyzer.pipeline`의 인사·단편 우회 및 판단 덮어쓰기 없이 수행할 예정이다.

이 72개는 **초기 비교 도구를 점검할 소규모 진단셋**이다. 학습 데이터나 few-shot/RAG 예문으로 넣지 않는다.
같은 문항·교정문·템플릿의 변형은 `group_id`를 참고하여 함께 격리하되, 현재 그룹 태그가 템플릿 중복을 완전히 검출한다고 가정하지 않는다.
문항이나 결과를 보며 프롬프트·모델·학습 데이터를 조정했다면 이후에는 개발용 진단셋으로 취급하고, 최종 성능 증명에는 별도의 미사용 고정 시험지를 만든다.

이번 자동 검사 통과는 문법 성능 측정이 아니다. 문법상 허용 33문항에서는 오교정 1건만으로도 관측 비율이 약 3.03% 변한다. 이 중에는 별도 표기 검수가 필요한 사례도 있다.
목표 과교정률 2% 이하를 입증하거나 운영 성능을 인증하기에는 표본이 작고 N4 오류 사례도 3개뿐이다.
향후에는 과교정률, 오류 탐지 정밀도·재현율, 명확한 문항의 처리율, 올바른 보류, JSON 성공률, 복합 오류 누락을 함께 보고한다.
보류·시스템 실패를 오류 탐지 성공으로 계산하지 않고, 분모·표본 수·검수 상태·신뢰구간을 함께 기록한다. 채점기는 이를 구현하며, 계약을 통과하지 못한 원시 결정을 공식 문법 점수로 승격하지 않는다.

문법 범위 참고: [국제교류기금 Irodori 초급 1](https://www.irodori.jpf.go.jp/assets/data/elementary01/pdf/Y_all.pdf).
참고 자료가 이 합성 시험지의 개별 정답이나 JLPT 태그를 인증하는 것은 아니다.

## 실제 STT 비중복 100건 계약 재시도 파일럿

기존 공식 50건의 인증된 입력 snapshot을 제외하고 실제 저장 STT 100건을 D 단독으로 실행했다. 비교정 원문 보존 위반에만 1회 재시도했으며 최종 계약 성공은 99/100, 재시도는 1건, 회복은 0건, 성공 99건 p95는 1108.711ms였다. DB는 읽기 전용이며 전후 SHA와 `judgment_results` 행 수가 동일했다. 원문 포함 원시 파일은 `evaluation/judgment/runs/shadow_v0.2/raw.jsonl`에 Git 제외 상태로 보관한다.

이 결과는 제한적 staging/shadow 기준 통과이며 문법 정확도나 운영 기본값 승인을 뜻하지 않는다. 세부 조건·해시·한계는 [100건 shadow 결과](../../training/judgment/JUDGMENT_D_SHADOW_V0.2_RESULT.md)를 따른다. `holdout_v0.4`는 모델 추론 0회 상태로 유지한다.

## 실제 STT 30건 독립 품질 검수 표본

기존 shadow 150건과 겹치지 않는 실제 저장 STT 30건을 문장 내용과 모델 출력에 무관한 고정 SHA-256 순위로 층화 추출했다. 검수자용 JSONL과 DB 매핑은 모두 `evaluation/judgment/runs/quality_review_v0.1/` 아래 Git 제외 경로에 있고, 추적 manifest에는 해시와 집계만 기록한다. 현재 상태는 `sealed_awaiting_independent_text_review`, 모델 추론 0회다.

실제 음성 파일이 없어 발음 정확도와 STT 전사 귀속은 평가하지 않는다. 검수 작성 규칙은 [독립 품질 검수 가이드](QUALITY_REVIEW_V0.1_GUIDE.md), 생성·완료 검사는 `build_quality_review_v0_1.py`와 `validate_quality_review_v0_1.py`를 따른다. 30건 라벨과 입력 해시를 봉인하기 전에는 모델을 실행하지 않는다.


사람 검수와 음성 평가는 현재 후순위로 보류한다. 표본을 개발·재학습에 전용하지 않고 봉인 상태로 보존한다. 원본 DB와 분리된 제한적 staging live 점검과 개인정보 없는 프로세스 로컬 상태 집계까지 완료했다. 실행·중단 절차는 [staging 가이드](../../docs/JUDGMENT_STAGING_RUNBOOK.md)를 따른다.
